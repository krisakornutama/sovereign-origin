# Security Review — teach.routes.ts (AI สอนลูก) — 2026-09-18

> ขอบเขต: ไฟล์ `sovereign-os/core-api/src/modules/knowledge/teach.routes.ts` (675 บรรทัด, 38 เส้นทาง)
> พร้อม service ที่มันเรียก (`teach-kids-*.ts`) — มุมมองเดียว: **ความปลอดภัยของเนื้อหาและช่องทางที่แตะเด็ก**
> สถานะก่อนรีวิว: **ไม่มีเทสเลย** (อันดับ 1 ของแผนที่ช่องว่างเทส §๙ ใน `docs/ops-runbook.md`)

## คำตัดสินรวม

**โครงสร้างปลอดภัยดีกว่าที่ตัวเลข 0% บอก** — ทุกเส้นทางผ่าน `authenticate` (JWT+MFA, ไม่มี dev bypass), เงินของเด็กถูกแยกโหมด play/real, PIN เก็บ bcrypt, คูปองแลกครั้งเดียว, ค่าใช้จ่ายมี audit log ตาม แต่**ความเสี่ยงที่ใหญ่จริงอยู่ที่ "เนื้อหาที่โมเดลสร้าง" ซึ่งวันนี้ไม่มีด่านกรองเลย** (R1) และ routes เดาสถานะ error จากข้อความ (R6) — ระดับความเสี่ยงจัดเรียงตามผลกระทบต่อเด็ก

## ความเสี่ยงเรียงตามลำดับควรแก้

### R1 — เนื้อหาบทเรียนจาก AI ไม่มีด่านกรองความเหมาะสม (สูงสุด)
- **ที่อยู่:** `POST /teach/generate` → `generateLesson` → `buildTeachPrompt` (`teach-kids-lesson.ts:156`) → `normalizeLesson` (ตัดยาว/จำกัดจำนวน เท่านั้น — ไม่ตรวจเนื้อหา)
- **ปัญหา:** ผู้ใช้ที่ผ่าน auth ใส่ `topic` อะไรก็ได้ ("ยาเสพติด", "อาวุธ", ลามก ฯลฯ) ระบบส่งตรงเข้าโมเดลและ**คืนเนื้อหาที่โมเดลตอบมาโดยไม่กรอง** — `normalizeLesson` เช็คแค่โครงสร้าง (สูงสุด 12 sections, quiz ≤10) ไม่มีบัญชีคำต้องห้าม ไม่มีการตรวจอายุ-ความรุนแรง และไม่มีการบังคับ `age_range` ให้ตรงกับที่ขอ
- **ทางลด:** กรอง topic ก่อนพร้อม (deny-list + ผ่าน `prompt-injection.guard.ts` ที่มีอยู่แล้วในระบบ), บังคับ system prompt ห้ามเนื้อหาผู้ใหญ่/ความรุนแรง + ตรวจผลลัพธ์รอบหนึ่ง (คำต้องห้าม/เรตอายุ) ก่อนคืน 200 — เทสชุดแรกควรยิงหัวข้อล่อและตรวจว่าถูกปฏิเสธหรือถูกกรอง
- **ตัวจริงที่ใกล้ตัว:** `stripThink` เหลือ markdown fence แล้วประกอบ HTML บนหน้าเว็บ — ถ้าโมเดล (หรือข้อมูล RAG ที่อาจมาจาก NOTE ที่คนอื่นเขียน) ใส่ `<script>`/`<img onerror>` มาใน content จะถูกเก็บลงคลังและเรนเดอร์ = **XSS โดนเด็กเป็นเป้า** — หน้า frontend ต้อง escape ให้เอง แต่ backend ควร sanitize ก่อน save (`/teach/save`)

### R2 — เกณฑ์อายุเป็นตัวเลือกที่ระบบไม่ผูกกับเด็กจริง (กลาง)
- `ageRange` มาจาก request (`default 6-8`) ไม่ใช่จากโปรไฟล์เด็ก — ผู้ใช้เลือกวัย "10-12" ให้เด็กวัย 5 ขวบได้ ภาษา/ความรุนแรงของเนื้อหาจึงไม่แนบกับตัวเด็กจริง · `AGE_GUIDANCE` เป็นข้อความสั่งโมเดลเท่านั้น ไม่มีการตรวจผลลัพธ์ว่าตรงระดับ
- **ทางลด:** เทสควรครอบว่า `ageRange` นอกรายการ → 400 (มีอยู่แล้ว) และพิจารณาผูก `kidId` → `age` ตอนเรียกจากหน้าเด็ก

### R3 — โหมดเงิน play/real อ่านค่าจาก DB เดียว ผูกกับเด็กดี แต่บางเส้นทางไม่เช็คโหมดก่อนทำรายการ (กลาง)
- `setKidMoneyMode` แยก play/real ชัด (`teach-kids-portfolio.ts`) — แต่ `buyStock/sellStock/piggyTransfer/payBill` ทาง API ไม่ได้ถามโหมดทุกจุด (ฝากเข้า service เป็นผู้กำหนด) และ `addWalletMoney` (เติม/หักเงิน) ไม่จำกัดสเกล (ใส่ 1,000,000,000 ได้) → ยอดปลอมทำแต้ม/เกียรติบัตรเพี้ยน แม้เป็น "เงินสอน" ก็ควรมีเพดาน
- **ทางลด:** เทสต้องจับสัญญา "ไม่มีทางลัดเงินโดยไม่ผ่าน requireKid + audit" และพิจารณา clamp ยอด

### R4 — PIN ของเด็ก: เก็บ bcrypt ดี แต่ไม่มี rate limit ต่อรองลอง (กลาง)
- `verifyKidPin` ใช้ bcrypt.compare ถูกต้อง และ PIN 4-6 หลัก (สูงสุด 1.1 ล้านค่า) — แต่ `completeChore`/`redeemCoupon` เรียกตรวจ PIN ผ่าน request ปกติ ไม่มีการจำกัดจำนวนครั้งลอง → เด็กคนอื่นที่ใช้บัญชีเดียวกัน (หรือคนในครอบครัว) brute force ได้ในเชิงทฤษฎี
- **ทางลด:** นับ fail ต่อ kid แล้วล็อกชั่วคราว (มี pattern ของ `accountLockout` อยู่แล้วในระบบ)

### R5 — คูปอง/งานบ้าน/บิล: สัญญาดีแต่ยังไม่พิสูจน์ (ต่ำ-กลาง)
- ของดีมี: แลกคูปองครั้งเดียว (`redeemed`), งานบ้านกันทำซ้ำ, ทุกการเงินเข้า `kidAuditLog`
- แต่ routes คืน 500 สำหรับข้อผิดพลาด service เกือบทุกจุด และ `addCoupon` ไม่จำกัด `cost` สูง (ตั้ง 999,999 ได้) · `deleteChore/deleteBill/deleteCoupon` ไม่ log audit ทุกจุด (ลบหลักฐานทางการเงินได้เงียบ ๆ)
- **ทางลด:** เทสครอบว่า "แลกแล้วหักจริงครั้งเดียว" + "ลบแล้วต้องมี trace"

### R6 — routes เดาประเภท error จากข้อความ (เชิงระบบ)
- ทั้งไฟล์จำแนก 404/403/400 จาก regex บน `err.message` เช่น `/kid not found/i`, `/PIN/i`, `/not enough/i` — ถ้า service เปลี่ยนข้อความ ผลคือ 400/500 สลับกัน เด็กเห็น error กำกวม และการเทสจะเปราะ · **ควร ref เป็น error class มี code** (ทำรอบเดียว ให้เทสอ่าน code ตรง)
- **ทางลด:** เทสชุดแรกอย่า assert ข้อความล้วน ให้ assert HTTP status เป็นหลัก (ตามที่วางไว้ในแผนเทสด้านล่าง)

### R7 — `/teach/save` เก็บ NOTE เข้าคลังความรู้โดยไม่จำกัดบทบาท (ต่ำ)
- ทุกคนที่ผ่าน `authenticate` (OPERATOR ด้วย) บันทึกบทเรียนเข้าคลังได้ แล้วบทเรียนนั้นจะกลายเป็น "ข้อมูลจากคลัง" ที่ RAG ใช้สอนเด็กทุกคน — เนื้อหาปลอม/เอียงจึงแพร่ข้ามเด็กได้
- **ทางลด:** จำกัดบทบาทผู้บันทึก (SUPERADMIN/พ่อแม่) + ทำเครื่องหมายแหล่งที่มา ("NOTE จากผู้ใช้") ใน prompt

## จุดที่ผ่านการรีวิวแล้วว่า "ปลอดภัยแล้ว" (อย่าทำซ้ำ)
- ทุกเส้นทางมี `authenticate` — ไม่มี route ใด public (ไล่ครบ 38 เส้นทางในไฟล์)
- `authenticate` ตัวกลางบังคับ MFA + ห้ามข้ามถ้า `must_change_password` (`auth.middleware.ts:33-40`)
- PIN: bcrypt hash ตอนเก็บ, เทียบด้วย compare, ล้างเป็น null ได้, ตรวจรูปแบบ 4-6 หลัก
- โมเดลขาออกถูก normalize/clamp ขนาดทุก field (หัวข้อ 200, content 4,000, quiz ≤10, options 300, sources ≤12)
- การเงินเด็กแยกบัญชีต่อเด็ก + audit log + งานบ้านกันทำซ้ำ + คูปองแลกครั้งเดียว

## แผนเทสเสนอต่อ (เมื่อเริ่มเขียน — ยึด HTTP status เป็นหลัก ไม่ยึดข้อความ)
1. สิทธิ์: ไม่มี token → 401 ทุกเส้นทาง (สุ่มแทนทุกกลุ่ม)
2. `/teach/generate`: topic ว่าง → 400 · ageRange บิดเบี้ยว → 400 · quizCount 0/11/1.5 → clamp/400 ตามสัญญา · Ollama ล้ม (mock deps) → 500 พร้อมข้อความ "ไม่ตอบกลับ"
3. `/teach/save`: lesson ว่าง → 400 · lesson ปลอมที่มี script tag → บันทึกได้แต่ต้อง sanitize (ตั้งเป้าด่านนี้หลังแก้ R1)
4. เด็ก/งานบ้าน/บิล/กระเป๋าเงิน: วงจรสร้าง→หัก→audit ตามสัญญาเงิน (ต่อ R3/R5)
5. PIN: ตั้ง/ล้าง/PIN ผิด → 403, ไม่มี PIN → เดินต่อได้, format ผิด → 400
6. หุ้นจำลอง/คูปอง: แลกครั้งเดียว, คะแนนไม่พอ → 400, หน่วยหุ้นไม่พอ → 400

> สรุปสั้นสำหรับตัดสินใจ: แก้ R1 (+sanitize ของ `/teach/save`) ก่อนเสมอ — เป็นด่านเดียวที่ "ความผิดพลาด = เด็กเห็นของไม่เหมาะวัย" โดยตรง · ตัวอื่นเป็นงานคุณภาพ/ความแข็งแรงที่เทสชุดแรกจะช่วยตรึงสัญญาไปพร้อมกัน
