# Skill Execution — วินัยในการปฏิบัติสกิลที่เปิดใช้แล้ว

สกิลนี้ไม่ได้สอนงานใหม่ — มันสอนการทำงาน**ทันทีหลัง skill ถูก activate** เป้าหมายเดียวคือ: สกิลที่ตัวเองอ่านไปแล้วต้องถูกปฏิบัติจริงทุกขั้นที่ขอได้ และขั้นที่ทำไม่ได้ต้องถูก**รายงานตรง ๆ** ห้ามหายเงียบ

ทำไมต้องมีสกิลนี้: ครั้งส่วนใหญ่ที่งาน "ใช้สกิลแล้วไม่เวิร์ก" ไม่ใช่เพราะสกิลแย่ แต่เพราะผู้ทำงาน (1) ลืมอ่านตัวสกิลจริงแล้วเดาหัวข้อจากชื่อ, (2) กระโดดข้ามขั้นที่ต้องพิสูจน์, (3) ขยายงานเกินที่สกิลขอ, (4) ปล่อยขยะชั่วคราวค้างใน repo, (5) สำเร็จ "ครึ่งทาง" แล้วรายงานเหมือนจบเต็ม

## 1. อ่านสกิลจริงก่อนแตะงาน — ห้ามทำงานจากชื่อหรือความจำ

- อ่านไฟล์ SKILL.md **ทั้งไฟล์** ตั้งแต่ action แรกหลังถูก activate (อ่านซ้ำไม่ผิด — การอ่านถูกแทนด้วยหน่วยความจำกลางทางเป็นจุดเกิดบั๊กที่พบมากที่สุด)
- **ทำงานจากเนื้อไฟล์เท่านั้น ไม่ใช่จากชื่อ skill** — ถ้ามีรายละเอียดคลุมเครือเช่นปรัชญาดีไซน์ ให้ปัก **Subject / Audience / Single job of this page** เป็นประโยคตรง ๆ ก่อนแตะงานแรก
- ไฟล์ทุกอย่างที่สกิลพูดถึงแบบ relative (สคริปต์, reference, template, font) ต้องถูก **resolve ต่อ directory ที่ user ระบุ** เสมอ ห้ามเดา path
- ถ้าสกิลอ้างสมบัติภายนอก (เช่น directory ฟอนต์) แต่ของจริงว่างหรือไฟล์ไม่ตรง — ห้ามนิ่งเงียบ: ประกาศทันทีว่าจะดึงจากแหล่งที่ user อนุญาตแทน (เช่น Google Fonts ตามลิสต์ที่สกิลรับรอง)

## 2. ทำตามขั้นของสกิลตามลำดับ — ขั้นไหน "คิด" ให้คิดใน thinking

สกิลหลายตัวพูดเรื่อง "two passes", "critique ตัวเอง", "อย่าโชว์ร่างแรก" — ขั้นพวกนี้ให้ทำ**ในช่อง thinking ของตัวเอง** ไม่ใช่กระจายเป็นข้อความหรือไฟล์ร่างหลายชุด:

- ขั้น brainstorm / critique / revision → ทำใน thinking ตามลำดับ แล้ว**เขียนไฟล์จริงครั้งเดียว**
- ขั้น "ส่งผลงานชิ้นเดียว" → ไฟล์เดียว ไม่ต้องมี `v2`, `_final`, `-test` มากมาย
- ขั้น "refine ของเดิม อย่าเพิ่มของใหม่" → ห้ามตอบโจทย์ด้วยการเติม graphic/ฟีเจอร์ ให้ปรับสิ่งที่มีอยู่ให้คมขึ้นเท่านั้น
- ขั้นที่สกิลปิดประตูชัด ๆ เช่น "Output only .md/.pdf/.png" → ไม่มีไฟล์อื่นหลุดรอดมาเป็นผลงาน

## 3. Fallback ต้องพิสูจน์เองก่อนใช้

สกิลไม่สามารถรู้เครื่องของคุณได้ทั้งหมด — มันจะสมมติว่ามี subagent, มี browser, มี Python, มีฟอนต์ในเครื่อง เมื่อของจริงไม่มีอย่างนั้น:

- **สำรวจสิ่งที่มีจริงก่อนตัดสินใจ** (ตัวอย่างจากงานจริง: ไม่มี subagent → ไม่ spawn baseline แต่ยังขับเคลื่อน test จริงผ่าน headless script; ไม่มีฟอนต์ใน `canvas-fonts/` → ดึงจาก Google Fonts ตามลิสต์ที่สกิลรับรอง)
- **Fallback ทุกตัวต้องพิสูจน์ทำงานจริงก่อนนำไปเป็นของหลัก** (รันครั้งเดียวจบ = ยังไม่เชื่อ; ของชำรุดต้องโดนจับจากสคริปต์ทดสอบ ไม่ใช่จากตาผู้ใช้)
- บันทึกทุก fallback ที่ใช้ลงรายงานท้ายงาน — ทั้งสิ่งที่ทำแทนและเหตุผลที่ตัวเลือกตามสกิลใช้ไม่ได้

## 4. พิสูจน์พฤติกรรมของผลงาน — ไม่ใช่แค่ "ผ่านด่าน" หรือ "เห็นว่ารัน"

การพิสูจน์หมายถึงการขับเคลื่อนของจริงเห็นพฤติกรรมจริง — ไม่ใช่แค่รัน build ผ่านหรือแค่เห็น command สำเร็จ:

- งาน logic/state → เขียนสคริปต์ headless ขับ lifecycle จริงและ assert state เปลี่ยนตามคาด
- งานเว็บ/เรนเดอร์ → ยิงจากเบราว์เซอร์จริง (หรือ Playwright headless) ตรวจ DOM/computed styles + นับ FAIL ที่จริง แล้ว**จับ FAIL ที่เป็นบั๊กตัวเองแยกจาก FAIL ที่เป็น flake ของเครื่องมือ** — บั๊กตัวเองแก้, flake ของเครื่องมือรายงานพร้อมหลักฐานการรันซ้ำ
- **ห้ามลบสคริปต์พิสูจน์ทิ้งก่อนรันจบ** — เก็บไว้จนได้ผลลัพธ์ครบ แล้วจึงเก็บกวาด

## 5. เช็คลิสต์ก่อนส่งมอบ

- [ ] ผลงานเดียวจบ ไม่มีร่าง/ไฟล์ทดสอบหลงเหลือใน tree ที่จะส่ง
- [ ] อ่านของจริง: ไฟล์ผลงานถูกสร้างจากเนื้อสกิล ไม่ใช่เดา
- [ ] ทุกขั้นของสกิลถูกปฏิบัติ (หรือมี fallback ที่พิสูจน์แล้ว) — ไม่มี "ขั้นที่ข้ามไปก่อน"
- [ ] ทุกข้อที่สกิลระบุ "ห้าม/จำเป็น" ยังอยู่ครบในผลงาน (เช่นกฎเรื่อง overlap, กฎเรื่องขอบ, กฎเรื่อง 90% visual)
- [ ] รายงานท้ายงานระบุชัด: สิ่งที่สร้าง, fallback ที่ใช้ (พร้อมเหตุผล), ข้อจำกัดจริงที่ยังเหลือ, และผลของการพิสูจน์พฤติกรรม (ตัวเลข/ข้อความจริงที่วิ่งผ่าน)
- [ ] ทำสถานะสอดคล้องกับตัวเองเสมอ — ไม่มีการประกาศ "เสร็จ" ที่ไม่มีผลพิสูจน์รองรับ

## 6. ความเห็นแก่ตัวเล็ก ๆ ที่ช่วยงานใหญ่

- สถานะที่รายงานคือ "รู้ความจริงของเครื่อง" ไม่ใช่ "เครื่องน่าจะไหว"
- ทุกผลพลอยได้ที่ตกค้าง (ไฟล์ชั่วคราว, พอร์ตเซิร์ฟเวอร์ทดสอบ, ภาพ proof) ต้องถูกเก็บกวาดก่อนส่งมอบ
- ถ้าทำของหลุดโจทย์เกิน (ของสะสม) ให้ตัดก่อนส่ง — ของที่ user ไม่ได้ขอคือหนี้ที่ต้องจ่ายตอนรีวิว

## 7. รายงานท้ายงาน — โครงบังคับ

```
## สิ่งที่สร้าง (เด่นชัด อ่านจบใน 10 วิ)
## Fallback ที่ใช้ (ถ้ามี) — เหตุผล + หลักฐานว่า fallback ทำงานจริง
## ผลการพิสูจน์พฤติกรรม (ตัวเลขจริง, จำนวน PASS/FAIL, จุดที่แก้ระหว่างทาง)
## ข้อจำกัดจริงที่ยังเหลือ (รายงานตรง — ไม่เลี่ยม)
```
