> ต้องอ่านตรงนี้ก่อน เพื่อไม่เสนอทางที่ขัดกับเป้าหมายที่เจ้าของเลือกแล้ว

## D1 — "ขายให้คนอื่นติดตั้งเอง" หมายความว่าอะไรกับโค้ด

### สิ่งที่ต้องเป็นจริง
1. **ติดตั้งจบในคำสั่งเดียว/ไฟล์เดียว** — มีแล้วบางส่วน (`INSTALL.cmd`, `tools/agent-pack/`)
2. **แยกข้อมูลลูกค้าแต่ละราย** (tenant isolation) — ยังไม่ทำ
3. **อัปเดตเองได้โดยไม่พังทั้งฟลีต** — มี signed manifest + rollout % + rollback ใน runner แล้ว แต่ยังขาด "ตัวตัดสินใจหยุด rollout"
4. **เห็นสุขภาพของแต่ละราย** — เริ่มมีแล้ว (`TENANT_ID` label ใน metrics/access log)
5. **ถอน/uninstall ได้สะอาด** — ยังไม่มี

### ทางเลือกเรื่อง isolation (ยังไม่ตัดสิน — ต้องคุยกับเจ้าของ)

| แบบ | ข้อดี | ข้อเสีย | เหมาะเมื่อ |
|---|---|---|---|
| **1 เครื่อง = 1 ลูกค้า** (ตอนนี้) | ง่ายที่สุด · ไม่ต้องแตะ schema · ข้อมูลไม่ปนกันโดยธรรมชาติ | เราไม่มีศูนย์กลางเห็นทุกเครื่องพร้อมกัน (ต้องพึ่ง heartbeat) | ลูกค้าติดตั้งในบ้าน/ร้านของตัวเอง ← **ตรงกับ D1 ที่สุด** |
| Shared DB + `tenant_id` ทุกตาราง | เห็นภาพรวม · อัปเดตครั้งเดียว | ต้อง migration ทั้งระบบ + RLS + ความเสี่ยงข้อมูลรั่วข้ามลูกค้า | ขายเป็น SaaS บนคลาวด์ของเรา |
| Shared DB + PostgreSQL RLS | แยกข้อมูลที่ชั้น DB (ปลอดภัยกว่า) | ต้องตั้ง policy ทุกตาราง + connection role แยก | ขายเป็น SaaS แต่ต้องการความมั่นใจสูง |

**ข้อเสนอ**: เริ่มจาก **1 เครื่อง = 1 ลูกค้า + TENANT_ID** (ต้นทุนต่ำสุด, ตรงกับสินค้าที่ให้ลูกค้าติดตั้งเอง)
แล้วค่อยขยับเป็น shared DB เมื่อมีลูกค้าที่ต้องการให้เราโฮสต์ให้ (ถ้าอยากได้เงินแบบ recurring)

### สิ่งที่ยังไม่รู้ (ถามเจ้าของก่อนลงทุน)
- ตั้งราคา/ไลเซนส์แบบไหน: ขายขาด · รายปี · ต่อเครื่อง? → กำหนดว่าต้องมีระบบ license/activation ไหม
- ลูกค้าติดตั้งเองแล้ว **ใครอัปเดต** (ลูกค้ากดเอง หรือเราเข้าทาง tunnel)?
- ต้องการหน้าจอ "ศูนย์ควบคุมลูกค้าทั้งหมด" (fleet control plane แบบ balena) หรือพอใจกับ heartbeat + Telegram alert?
- จะให้เราโฮสต์ให้บางราย (hybrid) หรือขายเฉพาะ self-host?

## D2 — "ต้องขายต่อได้" หมายความว่าอะไรกับโค้ด

### สภาพปัจจุบัน
- มี `offlineQueue` (IndexedDB, write-behind) + `useOfflineSync` แล้ว
- **ยังไม่มี idempotency key กลาง** — ถ้า response หายกลางทาง (เน็ตหลุดหลัง server บันทึกแล้ว) การ retry จะสร้างออเดอร์ซ้ำ
- มี idempotency เฉพาะ 4 service: `agent-team`, `business-shop`, `fleet-enrollment`, `truth-watchdog`
- local read model (อ่านเมนู/สต็อกได้ตอนเน็ตหลุด) — **ยังไม่มี**

### ลำดับที่ควรทำ (หลัง Cold Soak)
1. **Idempotency-Key กลาง** ที่ middleware + ตาราง `idempotency_keys` (ต้อง migration → รออนุมัติ)
   - ฝั่งเว็บ: สร้าง key ต่อ "การกระทำของผู้ใช้ 1 ครั้ง" (ไม่ใช่ต่อ request) แล้วเก็บใน offline queue
2. **Local read model** สำหรับหน้าที่ต้องใช้ตอนเน็ตหลุด (เมนู, ราคา, สต็อกคงเหลือ) — cache ผ่าน service worker/IndexedDB
3. **Conflict resolution ที่เขียนไว้เป็นกติกา** (Last-write-wins ไม่พอสำหรับสต็อก/เงิน — ต้องมีทิศทางชัด)
4. **แสดงสถานะ offline อย่างซื่อสัตย์** — ผู้ใช้ต้องรู้ว่าข้อมูลยังไม่ขึ้นเซิร์ฟเวอร์ (มี badge บางส่วนแล้ว)

## D4 — "ยังไม่รู้ความต้องการลูกค้า" (เจ้าของ 27/10/69) → นโยบาย no-regret

เจ้าของบอกตรง ๆ ว่า *"ผมไม่รู้ความต้องการของลูกค้า ผมรู้แค่ว่าอยากพัฒนา"* — นี่ไม่ใช่ปัญหา แต่เป็น **ข้อมูลที่ต้องบันทึก**
เพราะมันบอกว่า D1 ("ขายให้คนอื่นติดตั้งเอง") เป็น **สมมติฐาน** ไม่ใช่ความจริงที่พิสูจน์แล้ว

### กติกาที่ใช้ตัดสินงานตั้งแต่นี้

| ประเภทงาน | ทำเลย / รอ | ตัวอย่าง |
|---|---|---|
| **No-regret** — ต้องมีไม่ว่าลูกค้าจะเป็นใคร | **ทำเลย** (ถ้าไม่ต้อง restart/migration) | ติดตั้งจบได้เอง · ใบตรวจเครื่อง/SUPPORT.txt · observability · backup/restore · ความปลอดภัย · ซ่อมบั๊ก |
| **ตัวเลือกเชิงสถาปัตยกรรม** — ถูกสำหรับลูกค้าบางแบบ | **รอหลักฐาน** | multi-tenant RLS · billing/license · fleet control plane รวมศูนย์ · แอปมือถือ |
| **เดาฟีเจอร์** — "น่าจะมีคนอยากได้" | **ไม่ทำ** จนมีคนขอจริง 2 รายขึ้นไป | โมดูลใหม่ · integration ภายนอก · ธีม/ลูกเล่น |

### วิธีเก็บหลักฐานความต้องการโดยไม่ต้องจ้างที่ปรึกษา
1. **ลูกค้ารายแรก = ตัวเราเอง** (บ้าน/ฟาร์ม/ร้านนี้) — ทุกครั้งที่เราเจอความลำบาก ให้บันทึกเป็นงานพร้อมบริบทจริง (QUEUE/STATUS) ไม่ใช่ความรู้สึก
2. **`SUPPORT.txt` จากเครื่องที่ติดตั้งจริง** = ข้อมูลความต้องการทางอ้อมที่ดีที่สุด (เขาติดตรงไหน = เขาต้องการอะไร)
3. **ฟีดแบ็กในแอป/หน้าเว็บ** — มีอยู่แล้ว (`feedback_notes`, survey บน /demo) แต่ต้องมีคนอ่านเป็นรอบ (ตอนนี้ยังไม่มีรอบสรุปสำหรับเครื่องที่ติดตั้ง)
4. **คำถามเดียวที่คุ้มถามลูกค้า**: "ถ้าระบบนี้หายไปพรุ่งนี้ คุณจะเสียอะไรมากที่สุด?" — คำตอบคือลำดับความสำคัญจริง ไม่ใช่ฟีเจอร์ที่เขาชอบพูดถึง

### สิ่งที่ *ไม่* ลงทุนจนกว่าจะมีหลักฐาน
- ตาราง `tenant_id` + RLS ทั้งระบบ (แก้ทีหลังแพง แต่แก้ก่อนมีลูกค้าแพงกว่า — เพราะอาจแก้ผิดทาง)
- ระบบ license/activation/subscription
- หน้าจอศูนย์ควบคุมลูกค้าหลายราย (มี heartbeat + `/api/metrics` พร้อมต่อยอดเมื่อถึงเวลา)
- แอปมือถือแยก · multi-region · Kubernetes

> ทางเลือกที่ปลอดภัยที่สุดตอนนี้: **1 เครื่อง = 1 ลูกค้า + `TENANT_ID`** (มีแล้วใน observability) — รองรับทั้งการขายแบบติดตั้งเอง
> และการรวมศูนย์ในอนาคต โดยไม่ต้องตัดสินใจเรื่อง RLS วันนี้

## หลักการที่ไม่เปลี่ยน (แม้จะมีเงิน)

- **Free-first**: ของที่ต้องจ่าย (คลาวด์/API ภายนอก) ต้องเป็น "ตัวเลือกเสริม" ไม่ใช่เงื่อนไขให้ระบบทำงาน
- **Self-host ได้จริง**: ข้อมูลของลูกค้าอยู่ในเครื่องลูกค้าโดยค่าเริ่มต้น
- **ไม่ทิ้งความสามารถเดิม**: คิวอนุมัติงานเอเจนต์ · signed update · runtime layers · backup 3 ชั้น · watchdog — สิ่งเหล่านี้คือจุดที่ระบบนี้ *นำ* คู่แข่งอยู่แล้ว
- **ทุกงานต้องมีเทสต์คุม** (AGENTS.md ข้อ 8) — "ลองรันแล้วผ่าน" ไม่นับ
